# 电话这条线的现场笔记 —— 看起来像 A、其实是 B 的那些坑

这一份不是「我们当时怎么做的」,而是**给一个环境完全不同的你**:先量什么、量出来什么走哪条路、
哪一步会骗你。每条都是踩过或量过的,不是推测;推测的会明说。

## 怎么读这一份

- 每条四栏:**现象**(在用户眼里长什么样)/ **真因** / **怎么判**(一条命令或一个特征,让你当场
  把两种可能分开)/ **别怎么误读**(最容易走错的那个方向)。
- 每条末尾一个验证级别:**`真机验过`** / **`只读过代码`** / **`只是推断`**。这是本工作区的纪律,
  不许含糊。
- 出处标在括号里,指向 `state/design/` 下的记录与交接。
- 专名(World、NapCat、KoishiRTC、SnowLuma、AVSDK、PulseAudio 等)不翻译。
- 写到环境专有的东西,一律用 `<占位符>`;取值方法紧挨着写。

## 0. 先把两个词钉住,不然下面半篇看不懂

- **桥**:`<你的主机>` 上那个进程,它对外只说一种话 —— 一条 WebSocket,路径 `/v1/stream`,Bearer 令牌。
  你的 World 只跟它说话,不跟 QQ 的其它口说话。
- **两套通话形状**:同一套栈里有**两个** HTTP 口,字段名不一样。第 1 节整节讲这个,它是这条线上
  最贵的一个坑(一次让它"每一通电话都被静静忽略")。

## 1. 对端给的"形状"与"身份"

### 1.1 通话对象:插件口叫 `phase`,守护进程那条 WS 叫 `state`

- **现象**:他打过来,桥那边**收到了**(插件口能看到 `phase=ringing`),可她的 World 一动不动,
  那通一直挂在响铃里。用户看到的是"没接听"。
- **真因**:上游有**两套**通话对象的形状,而 World 连的是**守护进程那条 WS**,不是插件口。

  | 谁给的 | 状态字 | 对方是谁 | id |
  |---|---|---|---|
  | 容器内**插件口** `/v1/calls/current`(6110) | `phase` | `callerUin` | 裸 id |
  | **守护进程那条 WS**(6120,World 连的就是它) | `state` | `targetId` | `${bootId}:${linkEpoch}:${id}` |

  解析器只读 `phase` ⇒ 永远读空 ⇒ 返回 null ⇒ `onCall` 根本不触发 ⇒ **每一通都被静静地忽略**
  (连"陌生号直接拒"都不会发生)。
- **怎么判**:抓一份**真的 payload** 看它是哪个口给的。守护进程那份里有 `state` / `targetId` /
  `createdAt`;插件口那份是 `phase` / `callerUin` / `inviteAt`。解析器要"有什么认什么"
  (`phase|state`、`callerUin|peerUin|targetId`、`inviteAt|createdAt`、`endedAt|updatedAt`)。
- **别怎么误读**:★ 包根 `README.md` 与 `cloud/README.md` 里那句**"状态字段是 `phase` 不是 `state`"
  只对插件口成立**;把它当普适结论写给 WS 用的解析器,正是本节这个坑的成因。这句与
  `cortico-world-phone.md` 第十节**互相矛盾**(见文末「互相矛盾/未定」清单)。
  (`真机验过`,见 design/cortico-world-phone 第十节)

### 1.2 通话 id 必须原样带走,不能自己重拼

- **现象**:`accept` / `hangup` 被拒,回执 `STALE_CALL`。
- **真因**:上游校验 id 前缀 `bootId:epoch:`,拿裸 id 去发一律被判过期。
- **怎么判**:回执里的 `code` 是 `STALE_CALL`。
- **别怎么误读**:别以为"id 只是个标识、重新拼一个一样的就行"。
  (`真机验过`,见 design/cortico-world-phone 第十节)

### 1.3 对方是 **uid**,不是一个手机号;而且号码"迟到"约 5 秒

- **现象**:他正经打来,第一瞬间被判成"陌生号,直接拒了"。
- **真因**:这套部署的 QQ 能力里写着 `loginIdentityMode: uid`,WS 上的 `targetId` 先给
  `u_…`(有时先是字符串 `unknown`,中间还出现过内部 id),**手机号约 5 秒后才补上**;
  而名单里放的是手机号 ⇒ 永远匹配不上。
- **怎么判**:看拒接日志里那串到底是 `u_…`、`unknown`,还是号码。名单里 **uin 与 uid 两个都放**;
  身份不明时**等一轮**(实测 5 秒,留余量取 6 秒),期间补全了就按真号判。
- **别怎么误读**:别以为"名单里放手机号是天经地义" —— 桥那一侧根本就没在用手机号。
  也别忘了"等一轮"要放在**响铃**那条路径上,不是"只在状态变化时动作"。
  (`真机验过`,见 design/cortico-world-phone 第十一/十二节)

### 1.4 她主动拨号,目标也是 uid

- **现象**:`phone_dial` 拨不出去,回执说"没配拨号目标"或上游 `CALL_BUSY`。
- **真因**:上游那条 `dial` 走的是 `peerUid`(`{peerUid: args.targetId}`),不是手机号;
  而且**已经有未结束通话时上游直接拒**。
- **怎么判**:配置里 `dial.target` 填 `u_…`;本地先拦一道"通话中不能拨",把 `CALL_BUSY`
  说成人话。
- **别怎么误读**:别把"能拨号"当成想当然 —— 先量能力表里 `dial => supported`。
  (`真机验过`,见 design/cortico-world-phone 第二十二节、交接5 §1/§7)

## 2. 那一句会把人引到"版本不支持"上去的上游文案

### 2.1 `Requires an exact audited QQ library, build, platform and architecture.` —— 一字符串两义

- **现象**:控制台/回执里只看到这一句,于是以为"这个 QQ 版本不支持挂断/接听/拨号"。
- **真因**:★ **同一句话在两种完全不同的情形里出现**,而且**只有 message、没有 code** 时最容易混:

  | 情形 | 能力表怎么说 | 真意 |
  |---|---|---|
  | **库哈希不在审计名单**(版本不对) | `unavailable` | 真的没有这个能力,static 不利 |
  | **宿主自杀重启的窗口里** | `supported: true` | 只是"原生能力还没就绪",几秒后会好 |

  第二种:对方挂断(或宿主自己出问题)时,AVSDK 的 ppapi 子进程退出 → 上游宿主**主动退出** →
  监督脚本(`while true … sleep 2`)**2 秒后拉起**;从这几秒到它原生能力就绪之间,
  **所有控制命令(accept/hangup/dial)都会被拒**,理由就是这一句。实测:她两次挂断正好落在
  这个窗口里(AV Host 那个 QQ 进程的启动时间夹在她两次挂断之间),而**她前一通的挂断是成功的**。
- **怎么判**:**读能力表,不看 message**。
  `GET http://127.0.0.1:6120/v1/status`(带 `Authorization: Bearer <桥令牌>`)
  → 看 `capabilities.hangup.supported`(或 `v1/capabilities` 于插件口 6110):
  `true` ⇒ 是重启窗口;`false`/`unavailable` ⇒ 真是版本问题。也可以直接核进程启动时间。
- **别怎么误读**:**别把这句话读成"这个 QQ 版本不支持"**。同一个构建、同一通电话的上一通,
  挂断可能刚成功过。工程的应对是:第一失败**自动等 2.5 秒再试一次**(上游自己就 `sleep 2`),
  再失败就把出路交给她(让他挂);并且 **`send()` 要把上游的 `code` 落进日志**
  (回执给人看、日志给排查用 —— 只有 `code`(`CAPABILITY_UNAVAILABLE`)能把方向掰回来)。
  (`真机验过`,见 design/cortico-world-phone 第二十三节;另见 整合A-评估 §约束一「cap('unavailable', …)」)

### 2.2 `submitted` ≠ 接通

- **现象**:命令回执成功,于是当成功报出去 —— 而他手机根本没人接。
- **真因**:回执 `status:"submitted"` **只表示"提交给了 AVSDK"**。
- **怎么判**:接通看通话的 phase/state 变成 `connected`(接起实测 `ringing→accepted→connected`
  **约 3 秒**)。
- **别怎么误读**:别把 `submitted` 写进"已接通"的事件或回执。`submitted` 与 `connected` 是两件事。
  (`真机验过`,见 plan §11.2、交接2 §3)

## 3. "卡住"有两张脸,而它挡住一切

### 3.1 过渡态卡住:`rejecting` **和** `ending`(还有 `accepted`/`dialing`)

- **现象**:两种都见过 —— ① 对方挂断后"再打就没人接";② 拒掉一通之后,"新通话**桥这边连记录
  都没有**"(新的邀请根本进不来)。
- **真因**:这些**天生过渡**的状态都在等一个**可能永远不来的原生 ACK**。上一版只把 `rejecting`
  当"卡住",所以没救 `ending`。
- **怎么判**:`GET /v1/status` 看 `calls[]` 里 phase 停在哪个过渡态、停了多久;再看新邀请进不进得来。
- **别怎么误读**:**"卡住"在我们脑子里只有一张脸,而对面有两张**。凡是"等外部 ACK"的过渡态,
  都按"它会永久停在那儿"来设计。
- **解套(唯一)**:重启 AV Host 换 bootId(`pkill -f '[a]v-host-profile'`,作者的 supervisor 会把它
  拉起来),之后那通才走到 `ended`(`nativeEndEvent: "host.restarted"`)。
  World 侧把这做成"进入过渡态就起表、停过 `stuckSec` 就报出来并跑
  `worlds.phone.ssh.recoverCommand`";容器里也放一份 `watchdog.sh`(认同一组状态),两边不冲突。
  (`真机验过`,见 design/cortico-world-phone 第十三节、交接3 §4、`cloud/watchdog.sh`)

### 3.2 过期的响铃邀请**不许接**

- **现象**:重启后,World 把一通**躺在响铃里 62 分钟、那头早没人在等**的邀请照接了 ⇒
  这个接听命令永远等不到原生应答,桥从此卡在 `Another control is pending`,**之后每一道命令都发不出去**
  (= 他说的"然后就打不通了")。
- **真因**:那是我自己为"World 比来电晚一步也能接上"新加的规则**连带的射程**:它把过期邀请也接了。
- **怎么判**:回执 `Another control is pending or the call is in the wrong phase`;
  `/v1/status` 里那通停在一个过渡态不动。
- **别怎么误读**:别为了"晚一步也接"就无条件接响铃中的邀请 —— **超过响铃超时线的一律拒**,
  并说明"接一个过期的邀请会把桥卡住"。
  (`真机验过`,见 design/cortico-world-phone 第十一节①)

### 3.3 `Another control is pending …` 连着三次 = 桥卡住

- **真因**:同一句**连着出现三次**就认定桥卡住,跑一次 `recoverCommand` 解套并投一条通知。
- **别怎么误读**:单次出现可能只是正常竞争,别一看见就重启。
  (`真机验过`,见 design/cortico-world-phone 第十一节③)

## 4. 音频:整条声音是哑的,而 `/healthz` 会骗你

### 4.1 缺 `pulse-no-move.so` ⇒ 她一个字也听不见、也说不出

- **现象**:栈起来了、登录成功、三个口都在听、`/healthz` 200,但她**整条声音是哑的**
  (一个字听不见也说不出)。
- **真因**:桥的 `audio/pulse.mjs` 的 `diagnostics()` 会对一个文件做 `access()`:
  `config.noMoveShim ?? <bridge>/audio/pulse-no-move.so` —— **文件不在就当"没钉住"**,
  于是 `mediaAuthorized()` 恒为假,`receiveAudio`/`sendAudio` 一律 supported=false,`desired()`
  也拿不到通话。它**不在源码包里**,要现编:`cd <桥源码树> && node bridge/audio/build-pulse-shim.mjs`。
- **怎么判**:读能力表(或 `pnpm bridgeprobe`)看 `receiveAudio/sendAudio` 是不是 `supported=false`,
  诊断里有没有一行 `refusing unpinned PulseAudio capture.`。
- **别怎么误读**:★ 两个 `.so` **不是一回事**:
  - `qq-pulse-guard.so`(在**安装目录**)—— 给 QQ 的 AV Host 用,`install.py` 会编;
  - `pulse-no-move.so`(在**源码树** `bridge/audio/`)—— 给桥自己的 `parec`/`pacat` 用,**要手动编**。

  上一轮只编了前者,所以"守卫已装"那句话对了一半。还有一条:**别拿 `/healthz 200` 当音频的绿灯**
  —— 那个后端当时只验了 `/healthz`,"守护进程起来了"不等于"它的音频通了"。
  (`真机验过`,见 design/cortico-world-phone 第九节、交接3 §4、`cloud/up.sh` 第 2.5 步)

### 4.2 桥的播放队列硬上限是 **2000ms** ⇒ 外发音频要按播放速度配速

- **现象**:她的声音丢了几秒(实测丢过 2.8 秒),或者"一个字、卡一下"的碎片。
- **真因**:上游 `bridge/audio/common.mjs` 的 `maxQueueMs: 2000`,它是**抖动缓冲**、不是给整句用的。
  一口气把整句灌进去 ⇒ `BRIDGE_ERROR: Audio output queue is full.`
- **怎么判**:日志里 `Audio output queue is full.`;收尾日志里 `wroteAudioMs / callDurationMs / maxLagMs`
  这几个数一比就知道桥吃不吃得下。
- **别怎么误读**:**单帧 400ms 没超,超的是"在途总量"** —— 别以为"帧小就安全"。做法是按播放速度
  配速(只领先队列上限的一部分),队列满时把那一块**放回队首重试**,宁可晚、不能丢。
  (`真机验过`,见 design/cortico-world-phone 第十五/十六/十九节)

### 4.3 通话中云侧播放链可能掉到 ~0.5 倍速(容量事实,不一定是故障)

- **现象**:她长句越积越晚,听起来"慢半拍"。
- **真因**:云侧那条**播放**链(桥 → 隔离 PulseAudio → AV Host → QQ)。同一台机器**平时**往麦那个
  sink 写 3 秒音频现实花 3.97 秒(≈实时),**通话中**掉到约一半。
- **怎么判**:收尾日志里的 `maxLagMs`(正常对话里只有 **0.9 秒**左右;只有"连着说很长一段"才涨)。
- **别怎么误读**:★ **别把它当"电话坏了"去追**。实测他"没什么感觉",一两分钟的正常对话里队列排得空。
  真要查的顺序:重启 AV Host → 换大机器 → 翻上游。**这是一个容量事实,`maxLagMs` 才是判据。**
  (`真机验过`,见 design/cortico-world-phone 第二十节、交接4 §2)

### 4.4 「控制台看得到她的回复,但听不到声」

- **现象**:控制台上她的正文照常出现,后半个通话却一点声音都没有。
- **真因**:`maxSpeakSec` 那道闸门自己坏了两处 —— ① `spokeMsInRound` 被**加了两遍**
  (入队按字数估一次、写出按真实时长又加一次);② 它**整通电话只复位一次**(在 `onConnected`),
  不是每一轮。闸门一合,之后整通都不再出声,而控制台照旧显示她的正文。
- **怎么判**:日志里一行 `这一轮她说的已经够长了,剩下的不念了`。
- **别怎么误读**:别往"嗓子/网络/密钥"上查 —— 那是三道**看得见**的检查都会过的方向。
  (`真机验过`,见 design/cortico-world-phone 第十八节)

### 4.5 同一条提醒报了三十几次:`stalled` 判定用错了"重新开始卡"

- **现象**:她上下文里那条"桥那头放不出声了…"的提醒,一通里报了三十几次。
- **真因**:判定用的是"每次**重新开始**卡",而每成功一帧就把 `stalledSinceMs` 清了 ⇒
  「拒绝 → 成功 → 拒绝」这种**边卡边走**的节奏每轮都算一次"新卡住"。
- **怎么判**:日志里那条提醒的计数。
- **怎么改**:卡够一段时间(实测 3 秒)才提醒,且**一通只说一次**。
  (`真机验过`,见 design/cortico-world-phone 第十九节)

### 4.6 静默跳过:音频按"块"丢弃 ⇒ 他听到的是"单字碎片"

- **现象**:"只说了『今天最值钱的东西…』,后面的全是片段,只有一个字的那种,还是跳着来的。"
- **真因**:那一版按"块"(一块 400ms ≈ 一两个字)丢超时的音频 ⇒ 听感就是"一个字、卡一下"。
- **怎么判**:日志里 `这一块排太久了,不念了`(按块丢)。要按**整句**一起丢,而不是按块。
- **别怎么误读**:最后他定的规矩是**一个字都不丢**(他自己能用 `phone_stop` 收尾,自动丢弃没有
  立足之地)。别自己"顺手"把自动丢弃加回来。
  (`真机验过`,见 design/cortico-world-phone 第二十/二十一节)

### 4.7 静默跳过:她写的东西被筛掉时,以前不留日志

- **现象**:她明明写了正文,电话里没有 —— 无头案。
- **真因**:她的话在合成前要过一道筛(markdown/代码/链接/emoji 会被去掉),被滤掉时**静默跳过**。
- **怎么改**:滤掉时留一条日志。同一类还有:音频被丢弃、被"排太久不念" —— 以前都是静默的。
  (`只读过代码`,见 design/cortico-world-phone 第十八节⑤、交接4 §7)

## 5. 嘴(嗓子)那一环:三道验证一道都看不见的"哑"

### 5.1 关思考的端点缺失 ⇒ 她整通电话一句都说不出,而三道验证一道都看不见

- **现象**:她那边显示成「卡住了 8 次 / 6 次,约 1 分钟没能说出话」;挂断后立刻"恢复"。
- **真因**:密钥是**按端点名**读的(`providers/registry.ts` 用 `join(providersDir, name)` 去读那里的
  `.env`)。为了让"通话中关思考"只对电话生效,旧做法是**从当前端点临时派生一份** `<>-phone` 再切过去
  —— **新名字下面没有 `.env`** ⇒ `secret()` 返回空串 ⇒ **整通电话每一次模型调用都是无密钥发出** ⇒
  全部失败 ⇒ 她一句都生不出来。
- **怎么判**:在 persona 那个包的目录里跑
  `corepack pnpm endpointcheck --deployment <部署目录> [--call]`
  —— 它把"端点表(在不在、有没有自己的 `.env`、密钥长度) / 接起挂断的切换 / `--call` 真发一次看
  items 里有没有 `reasoning`"三样摊开。
- **别怎么误读**:★ **typecheck 绿、单测绿、装载(`check:extension`)绿,而她在那头是静音** ——
  这三道验证**一道都看不见**这个坑。规矩是"每一环都要有一条能自己跑、且真的会看结果的检查":
  嗓子和路有(`ttscheck` / `bridgeprobe`),嘴这一环就是 `endpointcheck`。
  修法:**只认部署里真的存在的那一份**(存在就切、挂断切回;不存在就**什么都不做**,照原端点评跑
  —— 慢但能出声,并留日志 + 给她一条看得见的通知);**绝不合成**。
  (`真机验过`,见 design/cortico-world-phone 第十四节、交接3 §1)

### 5.2 「关思考」发的是 `reasoning: { effort: 'none' }`,**不是**"不写这个字段"

- **现象**:探针量错了形状,差点得出反向结论。
- **真因**:框架在"关思考"时发的是 `reasoning: { effort: 'none' }`(见
  `protocol/open-responses/context-helpers.ts`);**不写这个字段**的话,端点会按自己的默认档跑
  —— 实测照样思考(reasoning_tokens 1312,有一次把 2000 的输出预算全烧在推理上、一个字都没答)。
- **怎么判**:按**生产形状**重量:`effort:'none'` → `items=[message]`、`reasoning_tokens=0`、
  **269 毫秒**答完(开思考时是 20~38 秒)。
- **别怎么误读**:**先抓一份真 payload 再下结论**,哪怕只是"不写某个字段"这种看起来无害的差别。
  (`真机验过`,见 design/cortico-world-phone 第十四节②)

### 5.3 端点热改的"无声降级":通话中保存过一次控制台配置

- **真因**:如果选"就地改当前端点的 `spec.thinking` 并还原",他若在通话中保存过一次控制台配置,
  `thinking:false` 就被持久化 —— 她**平时也不思考了**,而且是无声的。
- **怎么判**:看 `providers/<端点名>/config.json` 里 `spec.thinking` 有没有被落下 `false`。
- **别怎么误读**:所以选"派生 + 用完即删 / 只切名字"这条路,原则是**原条目字节级不动**。
  (`只读过代码`,见 design/cortico-world-phone 第六节)

### 5.4 TTS 要**带头的 WAV**,不要裸 PCM

- **真因**:裸 PCM 没有元信息,采样率/位深/声道全靠假设;它哪天改了只会"听上去怪"而不报错。
- **怎么判**:要 WAV 自带头,从文件头读事实;再拿它自报的时长与按文件头算出来的交叉核对,对不上
  就明确失败。
- **别怎么误读**:别为了"省一次解码"去要裸 PCM —— 省下的是性能,赔上的是"错了也不报"。
  (`只读过代码`,见 design/cortico-world-phone 第六节)

### 5.5 三道验证全绿、桥也是通的,而她整通不说话:她的常驻规矩与这条通道打架

- **现象**:他打进三通电话,**每通都接通了(约 1 秒)**,他的声音也认出来了几段,而她
  **每通的回执都写「你出声 0 段」** —— 他听到的是整通静音,像"线不通",而线一点没坏。
- **真因**:这一包以前只有一条出声的路:**她写下的正文**。而 persona 的常驻规矩写着
  「Text you output directly, without a tool, is private thought. No one can see it.
  To be heard, use a speaking tool」;qq2 / pet / terminal 都各有自己的说话工具,**只有电话没有**
  (那五个全是控制类:接/拨/挂/停/状态)。于是电话成了**唯一一个"只有正文才算说话"、又唯一一个
  没有说话工具的通道** —— 她按规矩办(要说话用工具),电话上无工具可用,就沉默。
  雪上加霜的是**接通那条通知当时只讲了入站方向**("他说的每一句都会作为事件给你"),
  「正文会被念出去」只写在那一节长提示词里(前缀层),压不过那条短而硬的规矩。
- **怎么判**:不要看回执"接通了没有",要看**她那一轮到底有没有正文**:
  `data/runs/<runId>/transcript.jsonl` 里筛 `item.type === 'message' && role === 'assistant'` ——
  0 条 = 她一个字都没写(那一轮只有 `external_event_frame` → `end_turn`),那就不是线的问题。
  她的 reasoning 项里通常也有原话(那天她自己写着 "my written text in a turn IS my voice.
  I should just write!")。
- **别怎么误读**:★ **"她没有出声"和"线不通"在她那头长得一模一样**,而且**通与不通都看回执**
  也分不出来 —— 接通回执是桥的事实,不是她开口的证据。判据只能是"那一轮有没有正文"。
  修法(=0.2.0):**给她一个说话工具 `phone_say`**,并在接通那条通知里当场点明"你要说话就调它"。
  正文那条路保留不动(兼容),两条路说同一句只念一遍(`saidThisRound` 一轮一轮地去重)。
  (`真机验过`,2026-10-14:`r-20261014-190328-fe7a` 三通 0 段;对照 10-09/10-10/10-11 那 28 通里 21 通有声)

## 6. 发语音条那条线(silk):与 World / 嗓子无关

### 6.1 语音条发不出去 = 协议端 ffmpeg 那条路

- **现象**:工具回执 `[send failed] send_private_msg: retcode=1200 Command failed: /usr/bin/ffmpeg …
  -c:a ntsilk_s16le -f ntsilk_s16le …`,底下 `Requested output format 'ntsilk_s16le' is not a suitable
  output format`。QQ 上确实什么都没有。
- **真因**:新 NapCat 见到 `FFMPEG_PATH` **非空**就跳过自带的 Native Addon,改用命令行 ffmpeg;
  而命令行那条路要的是**打过 silk 补丁**的 ffmpeg,官方镜像里那个是原版 ⇒ 没有 `ntsilk_s16le`
  codec。而上游 `entrypoint.sh` 里就有一行 `export FFMPEG_PATH=/usr/bin/ffmpeg`,等于把闸门顶开。
- **怎么判**:① `docker exec <容器> tr '\0' '\n' < /proc/$(pgrep -f 'qq --no-sandbox')/environ | grep FFMPEG`
  —— 有值就是又回到命令行那条路了;② `docker exec <容器> ffmpeg -hide_banner -encoders | grep -i silk`
  —— 空 = 原版 ffmpeg;③ 看 NapCat 启动日志那行 `使用 Native Addon 适配器`(这个才对)。
- **别怎么误读**:
  - **只坏一个方向** —— 收他的语音走 `-f s16le`,原版 ffmpeg 就会做 ⇒ 「她听得到他、他听不到她」。
  - 合成那半是好的、与它**无关** —— MiniMax 的 mp3 已经落盘且有记账,**不要去查密钥/额度/网络**
    (那些失败的回执面不一样)。
  - 修法是**把 entrypoint 那行 `export FFMPEG_PATH=` 置空**,让它回到自带 addon;不要自己另造一个
    打过 silk 补丁的 ffmpeg(那是给将来埋活)。
  (`真机验过`,见 design/napcat-voice-silk-断线)

## 7. 部署与脚本层面:那些"字面上成功"的静默失败

### 7.1 桥**拒绝绑非回环地址** ⇒ 容器必须 `--network host` 或走隧道

- **现象**:宿主上 `curl 127.0.0.1:6120/healthz` 不通,而容器里通。
- **真因**:上游 `createDaemon` 里有一条硬约束(原话「桥接仅监听本机;远程部署请使用 SSH 隧道或
  本机 TLS 反向代理」),它**拒绝绑 `0.0.0.0`**。
- **怎么判**:容器用 bridge 网络时它的 `127.0.0.1` 是容器自己的,宿主的回环够不着。用 `--network host`
  后容器的回环就是宿主的回环,隧道 `-L 6120:127.0.0.1:6120` 直连。
- **别怎么误读**:**别指望"发布端口"** —— 它不肯听 `0.0.0.0`,发布也没用。
  ★ 另一条:**界面驱动版的桥(`cloud/sl-bridge.mjs`)没有这条限制** —— 反倒是**宿主网络时必须绑回环**
  (`127.0.0.1`),用 bridge 网络时才绑 `0.0.0.0`,否则等于把口暴露在公网上(见它的配置模板)。
  这一条"A 有、B 没有",别把老桥的约束当普适定律。
  (`真机验过`,见 design/cortico-world-phone 第二节、cloud/README 第一节、`sl-bridge.json.template`)

### 7.2 WS 握手三条硬条件(外加单对端)

- **现象**:连不上,或者 403/401,但看代码哪都没错。
- **真因**:握手是**硬条件**:路径 `/v1/stream`、**必须带 `Authorization: Bearer <token>`**、
  **不能带 `Origin` 头**(带了就 403)、**同时只允许一个对端**(第二条连接直接 403)。
- **怎么判**:`pnpm bridgeprobe --url ws://127.0.0.1:6120/v1/stream --token-file <令牌文件>`;
  分清楚 401(令牌)/ 403(Origin 或第二对端)/ 404(路径)。
- **别怎么误读**:Node 自带的 `WebSocket`(undici)**不能设自定义请求头**,而这里必须有
  `Authorization` ⇒ 客户端必须用 `ws` 这个包(它要写进 `dependencies`)。
  **还有一条**:查能力/查历史**别用 probe** —— 桥只允许一个对端,他的 World 正连着时 probe 会被 403;
  用插件口/桥的**只读 HTTP 口**(`GET /v1/status`)去读。
  (`真机验过`,见 design/cortico-world-phone 第二节、交接5 §4、交接8 §4)

### 7.3 `pkill -f daemon.mjs` 会把执行它的 shell 自己也匹配掉 ⇒ 脚本自杀、后半段静默不跑

- **真因**:那条命令的**命令行里就含这个字符串**,`pkill -f` 按完整命令行匹配 ⇒ 匹配到自己。
- **怎么判**:脚本跑到一半没了、后面的步骤一条日志都没有,而退出码看着正常。
- **怎么改**:用模式 `[d]aemon\.mjs`。同一族:`pkill -f '[x]message -title'`、`pkill -f '[a]v-host-profile'`。
- **别怎么误读**:别把这当"脚本没写完"。
  (`真机验过`,见 plan §10.3、交接1 §5、`cloud/up.sh` 第 4 步)

### 7.4 `docker restart/stop+start` 会**登出** ⇒ 要重扫码

- **现象**:容器的自动登录票据过期,退回二维码登录。
- **怎么判**:启动日志里提示走二维码;二维码在容器 `/app/napcat/cache/qrcode.png`(约每 2 分钟换一张)。
- **别怎么误读**:别把"重启后掉登录"当故障。要免扫码就得配免扫码密码。
  (`真机验过`,见 plan §9、交接1 §5)

### 7.5 登录被拒一次(`ErrType 1 ErrCode 10`)**不是风控**

- **现象**:扫上了但几秒后被拒。
- **真因**:NapCat **只在 `ErrCode 3`(码过期)时才换新码**,别的错误码当普通失败就停住。
- **怎么判**:人工**重起一次登录拿新码**、让同一个人再扫就成;别据此判"账号被风控"。
  (`真机验过`,见 plan §11.2、cloud/README 第三节)

### 7.6 插件口 6110 / OneBot 3001"没在听"可能是"**还没到那一步**"

- **现象**:容器起来了、WebUI 6099 在听,但 3001 与 6110 都没在听,日志里也没有插件管理器那串。
  很容易误判成"插件没装进去"。
- **真因**:生产那份 NapCat 是**原装的**(故意没打"数据目录固化"补丁),它要**等 QQ 报出账号数据
  目录才继续** ⇒ **登录成功之后才开插件管理器**。所以"没在听"在**没扫码之前是正常的**。
- **怎么判**:等扫码之后看三行日志 —— `[PluginManager] Opening plugin manager...` /
  `[Plugin: napcat-plugin-koishi-rtc-qq] Koishi RTC QQ bridge listening on 127.0.0.1:6110; media=true` /
  `Loaded 1 plugins`。缺了才是没挂上。
- **别怎么误读**:**"没在听"要分两种:一种是坏了,一种是还没到那一步。** 把老测试栈的同一段日志
  逐行比,就分得开。
  (`真机验过`,见 整合A-实施 §2)

### 7.7 `recoverCommand` / `remoteHost` 指旧容器名 ⇒ **静默失败**

- **现象**:电话看着正常,只有她想自愈的时候自愈没发生。
- **真因**:`worlds.phone.ssh.recoverCommand` 里写着容器名(如 `docker exec <容器名> pkill -f
  av-host-profile`);**每换一次容器名这一格都要跟着改,它不报错**。
- **怎么判**:核一下那一格里的容器名是不是当前那个。
- **别怎么误读**:同一族还有 `remoteHost` —— 容器重建后 IP 会变,症状是"隧道起来了、桥却连不上"。
  现取:`docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' <容器名>`。
  (`真机验过`,见 cloud/README 第八节、整合A-实施 §0.2、交接10 §2)

### 7.8 两个桥的令牌**不是同一个**;401 是**静默**的

- **现象**:换线(换桥)后,看着什么都对,只有 `phone_status` 里能看见 401。
- **真因**:A 那条老桥的令牌与界面驱动版的令牌是两串不同的随机串(长度也不同);令牌是 World
  **启动时读一次** ⇒ 换完要重启。
- **怎么判**:核 `.env` 里的 `PHONE_BRIDGE_TOKEN` 与容器里那份 `control.token` 的**哈希**是否一致
  (只比哈希,别读内容;别打印令牌)。
- **别怎么误读**:**401 不像别的错误那样喊出来**,它只在 `phone_status` 里;换线时这一步最容易漏。
  (`真机验过`,见 交接11 §5)

### 7.9 容器里只有 C/POSIX locale:中文**不能**交给 `xdotool --name`

- **现象**:整条界面驱动**永远看不见来电窗**,而日志里**一句错都没有**。
- **真因**:`xdotool search --name` 拿 locale 处理模式,而这个容器只有 C/POSIX ⇒ `--name 语` /
  `--name 语音通话` 全返回空(`rc=1`);同一串字节交给 `grep` 就对得上(窗口名字本身是好 UTF-8)。
- **怎么判**:拿同一串字节分别给 `xdotool search --name` 与 `grep` 比;前者空、后者中 ⇒ 就是它。
  修法:改成"快路先试 `--name`,空手就列出所有可见窗 → 把名字拉回来在 JS 里比"。
- **别怎么误读**:别以为"窗口名是坏的"或"来电窗没弹出来"。
  (`真机验过`,见 交接10 §1.2、cloud/README 第九节)

### 7.10 模态对话框**会吃掉合成点击**;点完**必须验**,不许"点完就报成功"

- **现象**:控制台说"接了",他手机一直没人接。
- **真因**:来电窗上弹了一个模态框(「渲染资源初始化失败,显示驱动不兼容」),Qt 模态对话框**拦住
  下层窗口的鼠标事件**,点接听那一下被吃掉;而桥**点完就把 phase 设成 `connected` 并推给 World**,
  **没有任何"点到了没有"的验证** ⇒ 桥在这件事上说了谎。
- **怎么判**:抓一张点击**前**的图看有没有模态框(「我知道了」那颗在窗口内约 `(275,378)`);
  接通要看**布局真的变成通话中 / PulseAudio 里真的出现通话流**,而不是信回执。
- **别怎么误读**:别信"桥说 connected"。这**不是**某个版本的特殊 bug,而是**设计缺陷**:
  凡是像素驱动,点完都要验;验不过照实报失败。
  ★ 债务:这条**还没修**(见 route-b 那份)。另有一个"把点击吃掉"的近亲:窗口刚映射就点会点空,
  要**抬窗 + 等一拍再点**(`windowraise`/`windowactivate` + `readyDelayMs`)。
  (`真机验过`,见 交接11 §1.2/§1.3、cloud/README 第九节)

### 7.11 白板:GPU 进程起不来 + 镜像默认禁了软件光栅化

- **现象**:QQ 主窗卡成一整块白板,`unmap/map`、改尺寸逼重绘都救不回来;进程与渲染进程都活着,
  日志里当时没有崩溃行。**只有 `supervisorctl restart qq`,而重启 = 回登录界面 = 重扫码。**
- **真因**:Xvfb 里 Chromium 起不了 GPU 进程(`GPU process launch failed: error_code=1002`),
  而镜像默认参数里又有 `--disable-software-rasterizer` —— **把软件渲染这条唯一的退路也堵死了**。
- **怎么判**:容器日志里搜 `GPU process isn't usable` / `error_code=1002`。
- **别怎么误读**:★ 修法有**取舍**:去掉 `--disable-software-rasterizer` 能治白板,但会**换来**
  "渲染资源初始化失败"那个模态框(见 7.10)。两条是同一处权衡的两头,别以为有一劳永逸的开关。
  (`真机验过`,见 交接9 §2.3、交接11 §1.3)

### 7.12 apt 的三个坑(都已解决,别再撞)

- ① 默认源解析成 **IPv6**,阿里云 ECS 没 IPv6 ⇒ 不换源会卡死;② 容器里的 `linuxqq` 自己缺
  `xdg-utils`,导致整个 apt 处于"依赖不满足",**任何包都装不进去** ⇒ 必须先单独装它;
  ③ **永远别用 `apt-get -f install`**(可能把 `linuxqq` 卸掉)。
  (`真机验过`,见 plan §9、交接1 §5)

### 7.13 上游 `scripts/probe.py` 用 Python 3.11 的 `hashlib.file_digest`,容器是 3.10 ⇒ 报错

- **怎么判**:`AttributeError: module 'hashlib' has no attribute 'file_digest'`。
- **别怎么误读**:**是它的 bug**,别去改配置、别去装 Python 3.11。
  (`真机验过`,见 plan §10.3)

### 7.14 远程 CLI 的坑(概括)

- exec 的**超时不回输出**(长命令一律后台跑 + 写日志 + 轮询);
- 路径会被你本机的 shell **改写**(如 Git Bash 把 `/opt/...` 翻成当前盘根)⇒ 需要时加
  `MSYS_NO_PATHCONV=1`;
- `download` 跑在**宿主**上,容器里的路径要写成宿主对应的路径;目标文件已存在会**交互式问覆盖**。
  (`真机验过`,见 交接1 §5、交接2 §7)

### 7.15 上游/第三方 CLI 的版本坑(与 7.14 同类,单列一条)

- 某个版本的远程 CLI 的 **exec 通道是坏的**(报 `missing port in address`),**download 通道正常**;
  换一个修好的版本即可。别一上来就怀疑网络。
  (`真机验过`,见 交接1 §11)

## 8. 配置声明与"验证本身"的坑

### 8.1 `type:'array'` **只支持"两个数的区间"** ⇒ `callers` 名单进表单会被压成 `[号, 0]`

- **现象**:他部署的 `config.json` 里,**我声明过的每一个表单旋钮都写下了**(连空数组都在),
  **唯独少的正是 `callers`(接听名单)** —— 而那是唯一必须填、也最容易悄悄配错的东西。
- **真因**:框架的配置 `type:'array'` **不是通用列表**:`config-schema.ts` 的 `readGroupValues`
  把它强制成 `[Number(pair[0])||0, Number(pair[1])||0]`,写入侧 `needsPair` 还要求 `raw.length === 2`
  —— 只支持"两个数的区间"(mouse 的 `moveDurationMs = [60, 700]` 就是它)。N 个号的名单挂进表单
  只会被压成 `[号, 0]`。既有规矩是:列表类配置**都不进表单**,只从 `config.json` 改。
- **怎么判**:把名单那格从配置组里删掉(配置段与默认值保留);`callers` 只能在 `config.json` 里改。
- **别怎么误读**:★ **`check:extension` 也照样过** —— 声明得"合法但不符合框架的真实语义",
  是那种只能靠"把约定写成断言"才防得住的东西(所以要有一条回归测试逐条核"声明过的路径在
  `defaults()` 里有对应项、类型相符、`array` 只许两个数的区间、列表类不进表单")。
  (`真机验过`,见 design/cortico-world-phone 第八节)

### 8.2 后加的配置格**必须容错读**

- **现象**:他在控制台里点了某个新工具,整通启动崩掉。
- **真因**:他部署里那份 `config.json` 比这个键**早写** ⇒ 直接读 `cfg.dial.target` 会崩;
  而这类崩**单测看不出来**(测试里总是新配置)。
- **怎么判**:缺键 / 类型不对 / 空串一律当"没配",工具回执明说"没配…",而不是静默失败。
  (`真机验过`,见 交接5 §7)

### 8.3 假件必须与真件**同形**,否则等于没测

- **现象**:94/108 条测试全绿,**而真机上一通电话都不认**。
- **真因**:单测里的假桥用的是"我以为的形状"(`phase`/`callerUin`),而真件是另一套
  (`state`/`targetId`)。假件与真件不同形 ⇒ 测的只是自己的想象。
- **怎么判**:凡"按对端给的形状解析"的层,**测试里的假件必须照抄真件的原文**。抓一份真 payload
  存进测试,是最便宜的一道闸。
- **别怎么误读**:别把"测试全绿"当"对端认同你的形状"。同一条线还有一句:
  **"真件的行为顺序也是契约的一部分"** —— 号码迟到、更新分好几条、命令会卡住,这些是**时序**,
  抓真日志(而不是只看字段)才看得见。
  (`真机验过`,见 design/cortico-world-phone 第十/十一节、交接3 §8)

### 8.4 收尾要打印的量,**绝不在收尾路径上清零**

- **现象**:收尾日志里 `wroteAudioMs / staleDroppedMs / stallNoticed` 永远是 0。
- **真因**:这些是"一整通"的账,而清零写在 `finishCall` 里、日志又是收尾时打的 ⇒ 永远打印 0。
- **怎么判**:改成只在**接起时**清。
- **别怎么误读**:别为了"清干净"把要打印的量清没了。
  (`真机验过`,见 design/cortico-world-phone 第二十节②)

### 8.5 "她发起的动作没成功"必须有一句话

- **现象**:她拨出去没接通、她按停没按到、她写的东西没被念 —— 她**以为成功了**,于是等一个永远
  不来的回复;这些在她看来**都长得像"什么都没有发生"**。
- **真因**:这三件都属于"她那侧的静默"。
- **怎么判**:一条事件就是这一层的全部可见性(`phone.outgoingFailed` 等)。判据可以很干净:
  "接通才会置 `announced`,所以 `announced === false && direction === 'outgoing'` 精确地只有
  '她拨了、没接通'这一种"。
  (`真机验过`,见 交接5 §7)

### 8.6 判据要写清**"宁可漏还是宁可误杀"**

- **例子**:识别猜错的语言那一条,选了"宁可漏"(**不碰 `auto` 下的拉丁短词** —— `OK`/`Yeah`
  可能真是他说的),因为**误杀真人话比漏掉一句噪声贵得多**。
- **怎么判**:这个取向要**写进注释**,不然下一个人会"顺手"把它调严。
  (`只读过代码`,见 交接5 §7、design/cortico-world-phone 第二十二节)

## 9. 互相矛盾 / 未定的地方(照实记,别当已定)

### 9.1 矛盾

1. **`phase` vs `state`**(见 1.1)。包根 `README.md` 与 `cloud/README.md` 曾把它写成一句普适结论
   ("状态字段是 `phase` 不是 `state`"),而 `cortico-world-phone.md` 第十节证明**守护进程那条 WS
   用的是 `state`/`targetId`**。**矛盾点**:README 那句只对**插件口**成立,对 World 连的那条 WS
   是**反的**。以第十节为准。**→ 两处 README 在打包这个仓库时已经改成"两套写法 + 有什么认什么",
   这条矛盾已消**。
2. **0.5 倍速算故障还是容量事实**。`cortico-world-phone.md` 第二十节把它当"根因/瓶颈";
   `交接4` §2 明确写"**不要把它当成电话坏了去追** —— 他自己实测没什么感觉,`maxLagMs` 才是判据"。
   **矛盾点**:同一现象一处叫"根因"、一处叫"容量事实"。建议口径:它是容量事实,`maxLagMs` 是判据。
3. **`nativeCommands` 的条数**。plan §11.1 列了 11 个号(`[1,5,55,4,10,9,8,13,57,43,14]`);
   交接11 §5 说"nativeCommands **12 条**"。**矛盾点**:两个数不一致,且没有一份给出完整清单。
4. **`recoverCommand`/watchdog 认的状态集合**。`cloud/README.md` 第四节与 `cloud/watchdog.sh` 的
   注释写"卡在 **`rejecting`** 超过 60 秒",而 `watchdog.sh` 的**代码**认的是
   `ending|rejecting|accepted|dialing` 四种。**矛盾点**:文字落后于实现,以代码为准。
   **→ `cloud/README.md` 那句在打包这个仓库时已经改成四种并列了**,`watchdog.sh` 的 case 未动。
5. **A 的桥 vs B 的桥,绑不绑回环**。老桥**拒绝**绑非回环(7.1);界面驱动版**允许**绑
   `0.0.0.0`(bridge 网络下要绑,host 网络下要绑回环)。**矛盾点**:"桥只肯绑回环"只对老桥成立,
   别当普适定律。

### 9.2 未定 / 未验(明说,别当已定)

- **界面驱动路(B)的端到端没验过**:协议层在真环境验过(握手四种情形、单对端、同 id 幂等),
  **端到端(真来电窗 + 他的手机)没验过**;`dial` 不支持;认不出打电话的人是谁。
  (见 route-b 那份、design/cortico-world-phone-交接8/9/10/11)
- **B 的 Windows 版没写过**:`cloud/sl-bridge.mjs` 是 Linux/X11 + PulseAudio 专用;Windows 要另写
  "看屏幕 + 搬音频"那半(窗口查找/点击/抓图那节),**它在本机只有形状、没有实测**。
  (见 交接12 §3)
- **B 的"点完要验"还没修**(7.10 的债务)。(见 交接11 §3)
- **登录窗上勾"自动登录"会不会持久化**:未验证。(见 交接9 §2.3)
- **主动拨的界面入口"点下去本该发生什么"仍然未知**(搜索框不弹结果、资料卡那颗钮点了两次都没拨
  出去)。(见 交接9 §2.2、交接10 §6)
- **SnowLuma 在无头 Linux 上的两个未修 bug**(注入后周期性 SIGABRT / 已登录但一直等登录):
  **在这台机器上没有复现**,但同类 bug 清单里的版本恰好包括其官方镜像自带的那个 ⇒
  **换一台机器是否复现,未知**。(见 交接8 §3.3/§3.4、交接9 §1.1)
- **账号风控**:照实说 —— **不知道**,不是安全。(见 plan §六)
- **MiniMax 一句的合成耗时**有两处口径:plan/设计写"1~3 秒",交接3 实测"1.2~1.4 秒"
  —— 取实测值更准,但**随负载变**。
- **`asr.language`**:建议显式填 `zh`(自动判定会把中文碎片猜成英/日/韩)。这条是建议值,
  不是硬规矩 —— 不同环境里从 `auto` 改 `zh` 的收益要自己重量。
  (见 design/cortico-world-phone 第十七节、交接4 §1)
